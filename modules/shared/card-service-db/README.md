# TAG Card Service - Aurora Postgres Cluster

The Card Service Aurora Postgres cluster is a Global Aurora cluster with the primary cluster in us-east-1 and the secondary in us-west-2.

The Postgresql Database containing all the Card Service data is the `cards` Database.

## Applying Terraform changes to an environment

1. Initialize Terraform:
    ```bash
    terraform init -backend-config=envs/${env}/${env}.backend
    ```
1. Generate a Terraform plan:
    ```bash
    terraform plan -var-file=envs/${env}/${env}.tfvars -out tf.plan
    ```
1. Carefully review the plan in `tf.plan`
1. Apply the changes:
    ```bash
    terraform apply tf.plan
    ```

## Read Terraform outputs for an environment

1. Initialize Terraform:
    ```bash
    terraform init -backend-config=envs/${env}/${env}.backend
    ```
1. Read the outputs:
    ```bash
    terraform output
    ```

## Network Access

Network access to the primary and secondary clusters is currently granted to:
* The CIDRs of the VPCs in both regions (us-east-1 and us-west-2) of the deployment environment
* VPN internal IPs (Dev and Test env only)

### SG Access Limitation

Ideally VPC wide access would be reduced to only grant access to the following Security Groups:
* Card Service application
* Support box
* Fabric Github Runner
* VPN internal IPs (Dev and Test envs only)

This is currently not possible as the us-east-1 and us-west-2 VPCs of each environment are not peered and Security Groups in non-peer VPCs are not visibile via Transit Gateway.
In future if the Security Group visibility via Transit Gateway feature is added by AWS then we can updated the SG Rules to allow only the Security Groups that require access (refer:  https://repost.aws/questions/QUYHzCAeoFQ3CofUBWcKfUFA/transit-gw-using-vpc-security-groups).

## Database Users

Admin Postgresql Roles and Users are managed via Terraform.
Currently the `cards-database-owner` Role is the owner of the `cards` database; meaning it can manages all resources (tables, extensions, roles and users with access to `cards` DB etc).

The following Postgresql Users are allowed to login with the `cards-database-owner` Role:
* `github-actions-runner-iam`: This Role is for the Github Runner to use for database migration scripts to create Postgresql resources such as Tables and less privileged Users (application user, support user etc)

## Credentials

There are two type of database user available; password-based and iam-auth-based.

### Password based users

Password based user have their password stored in an AWS SecretsManager Secret. This is set by the `password_secret_name` attribute in the `postgres_users` Terraform variable for each password-based user. It also shows up in the `password_secret_name` attribute in the Terraform output attributes.

### IAM Authorization based users

IAM Auth users don't have a password. A short-lived (15 minutes) access token can be generated by an AWS API or the AWS CLI.

A fresh token can be generated by the AWS CLI with a command like:
```bash
aws rds generate-db-auth-token --hostname <cluster-uri> --port <cluster-port> --username <user-name>
```

The AWS CLI command to generate an auth token to use as a password for a specific IAM Auth user is available in the `auth_token_generation_command` attribute of the Terraform output attributes.

If an IAM Auth type user is utlized by an application then the application will need to use the AWS SDK to refresh the token.

### Backups

Automated database backups are controlled through the `backup_frequency` variable which can either be set to `daily` or `hourly`, depending on the AWS account being deployed to. By adjusting the `backup_frequency` variable, an AWS resource tag for `backuphourly` is set to `yes` or not set at all. This uses the existing policies setup by Cloud Engineering, see [AWS Backup plans](https://us-east-1.console.aws.amazon.com/backup/home?region=us-east-1#/backupplan) for more details.

Currently, the defaults are set so that backups are automatically enabled to prevent any scenario where they are not enabled in Prod environments.

#### Summary

For **production environments**, `backup_frequency` is defaulted to `hourly` so nothing would need to be added, daily/hourly/weekly/monthly backups plus bidirectional copying would be automatically enabled.

For **non-production environments**, the `backup_frequency` variable would need to be set to `daily` to ensure that backups are not `hourly`.

### Backup frequency and retention

#### In non-production environments:

- **Daily**: 4 days

- **Weekly**: 2 weeks

#### In prod environments:

- **Hourly**: 1 day

- **Daily**: 1 week

- **Weekly**: 2 weeks

- **Monthly**: 2 months

### Auto Minor Version Updates

Auto minor version updates are enabled for both primary and secondary clusters (`auto_minor_version_upgrade = true`). This means AWS will automatically apply minor version patches during the maintenance window.

**Important considerations:**
- Since we use the external [terraform-aws-modules/rds-aurora/aws](https://registry.terraform.io/modules/terraform-aws-modules/rds-aurora/aws/latest) module, we cannot add lifecycle rules to ignore engine version changes
- This typically won't cause issues as we maintain the latest minor version in our configuration
- **When upgrading major versions**: Always review and test the upgrade path thoroughly, as auto minor updates will continue to apply patches within that major version
